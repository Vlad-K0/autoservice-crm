# Title: M1-2 Vehicle: сущность, миграция, репозиторий

---

**Этап:** M1 — Ядро CRM · **Модуль:** `crm-clients` · **Размер:** M · **Зависимости:** M1-1 (паттерн подключения модуля)

## Что делаем

Центральная сущность системы — автомобиль. Поля — из обзора §3.1
(Torqvoice `Vehicle` + Odoo Fleet).

**Миграция `V3__vehicles.sql`:**

- таблица `vehicles`:
  - `id` (bigserial PK),
  - `vin` varchar(17) **unique** (nullable — не всегда известен),
  - `license_plate` varchar(15) not null (индекс — ключ поиска),
  - `make`, `model`, `generation` (марка/модель/поколение),
  - `year` (int, проверка 1900..текущий+1),
  - `body_type`, `engine`, `fuel_type`, `transmission`,
  - `last_mileage` int (обновляется из заказ-нарядов начиная с этапа 2),
  - `category`, `created_at`, `updated_at`.

**Код в `crm-clients`:**

- JPA-сущность `Vehicle`;
- репозиторий `VehicleRepository` (поиск по точному VIN / госномеру — методы `findByVin`, `findByLicensePlate`);
- сервис `VehicleService` (CRUD, нормализация: VIN и госномер → upper case, пробелы из госномера убрать).

## Готово, когда

- [ ] Миграция V3 накатывается, `ddl-auto=validate` проходит
- [ ] Повторная вставка VIN падает с нарушением уникальности (тест)
- [ ] Нормализация VIN/госномера покрыта тестами (`"в 123 ав 45"` → `В123АВ45`-стиль, upper case)
- [ ] `make test` зелёный

## Подсказки

- Привязка «клиент ↔ авто» — отдельная задача M1-3 (таблица периодов владения), в этой задаче связи с клиентом нет.
- Госномер храним нормализованным без пробелов в одном регистре — поиск будет точным.
- VIN может отсутствовать (старые авто, клиент не знает) — поэтому unique, но не not null.
