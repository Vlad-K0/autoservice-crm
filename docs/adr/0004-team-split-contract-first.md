# ADR-0004: Разделение работы по слоям + контракт-first

- **Статус:** принято
- **Дата:** 2026-11-07
- **Заменяет частично:** подход «вертикальные срезы на человека» из обсуждения ADR-0002 (сам ADR-0002 — про структуру репо, остаётся в силе)

## Контекст

Команда — два разработчика. Вертикальные срезы (один делает фичу от БД до UI)
хороши для обмена знаниями, но на старте медленнее: каждый ждёт полную
проработку чужого слоя. Команда решила параллелиться по слоям:
бэкенд (Java) — один, фронтенд — второй.

## Решение

1. **Слойное разделение:** backend/ — один человек, frontend/ — второй.
   Внутри бэкенда доменные модули и правила ADR-0002 не меняются.
2. **Интерфейс между слоями — OpenAPI-контракт** `docs/openapi/crm-api.yaml`.
   Единственный источник правды об API. Меняется только через PR,
   который ревьюят **оба** (см. CONTRIBUTING, «Контракт API»).
3. **Фронтенд не ждёт бэкенд:** работает против мок-сервера из контракта
   (`make mock`, Prism на порту 4010) и типизированного клиента,
   сгенерированного из контракта.
4. **Бэкенд сверяется с контрактом:** реализация обязана соответствовать
   контракту; расхождение — баг. (Позже можно добавить contract-тесты,
   сверяющие springdoc-выдачу с yaml.)

## Последствия

- Максимальная параллельность с первого дня; конфликты в git минимальны
  (каждый в своей папке).
- Риск bus factor повышается (каждый знает «свой» слой). Митигируется:
  обязательное кросс-ревью каждого PR (правило уже есть) — фронтендер читает
  API-изменения, бэкендер читает интеграцию; контракт — общее знание обоих.
- Регресс: смена API «молча» ломает фронт. Митигируется правилом контракт-PR.

## Альтернативы (отклонены)

- **Вертикальные срезы на человека** — лучше для bus factor, но медленнее
  на старте и требует от каждого полного стека; вернуться к нему можно позже,
  этот ADR не навсегда.
- **Backend-first без контракта** (фронт начинает после готового API) —
  последовательная работа вместо параллельной.
