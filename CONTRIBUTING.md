# Как мы работаем

Команда — два разработчика. Правил немного, но они обязательные.

## Ветки и коммиты

- `main` защищён: изменения — только через pull request.
- Работа ведётся в ветках `feature/<краткое-имя>` (например, `feature/clients-crud`),
  для правок — `fix/<имя>`.
- Коммиты — [Conventional Commits](https://www.conventionalcommits.org/ru/):
  `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`.
  Один коммит — одна логическая правка.

## Pull request

- Маленькие: до ~400 строк diff. Больше — режьте на несколько PR.
- Шаблон PR (`.github/PULL_REQUEST_TEMPLATE.md`) обязателен к заполнению.
- Merge — только после approve второго разработчика и зелёного CI.
- Ревью — обязательное для каждого PR: это и качество, и обмен знаниями.

## Definition of Done

Задача считается законченной, когда:

- [ ] Тесты написаны и зелёные (`make test`)
- [ ] Изменения схемы БД — **новым** файлом Flyway (чужие миграции не правятся)
- [ ] OpenAPI-контракт актуален (новые эндпоинты/поля отражены)
- [ ] CI на PR зелёный
- [ ] Ревью пройдено

## Разногласия

Спор о решении, который не решился за 15 минут, — значит, это архитектурное
решение: заводим ADR (см. `docs/adr/_template.md`), фиксируем варианты и выбор.
Финальное слово — за тем, кто больше времени работает в спорном модуле.

## Контракт API (контракт-first)

Работа разделена по слоям (бэкенд / фронтенд, ADR-0004). Единственный источник
правды об API — `docs/openapi/crm-api.yaml`.

Правила:

1. **Сначала контракт, потом код.** Любое изменение API начинается с PR в
   `docs/openapi/crm-api.yaml`. Такой PR ревьюят **оба** — это точка встречи слоёв.
2. **Фронтенд** генерирует клиент из контракта и работает против мока:
   `make mock` (Prism, http://localhost:4010), не дожидаясь бэкенда.
3. **Бэкенд** реализует эндпоинты строго по контракту; расхождение = баг.
4. **Breaking change** (удаление поля/эндпоинта, смена семантики) — только
   по согласованию в контракт-PR, с планом миграции фронтенда.
